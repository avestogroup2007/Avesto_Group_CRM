# Развёртывание

## Фронтенд — GitHub Pages (уже работает)

Публикуется автоматически при пуше в `main` (workflow `deploy-pages.yml`).
Адрес: **https://avestogroup2007.github.io/Avesto_Group_CRM/**

## Бэкенд — Render (Blueprint)

В репозитории есть `render.yaml` — он описывает веб-сервис + PostgreSQL.
Развёртывание в несколько кликов:

1. Зайдите на **https://render.com** и войдите через GitHub.
2. **New → Blueprint**.
3. Выберите репозиторий **`avestogroup2007/Avesto_Group_CRM`** (ветка `main`).
4. Render прочитает `render.yaml` и покажет, что создаст:
   - `avesto-crm-backend` — веб-сервис (Node);
   - `avesto-crm-db` — PostgreSQL.
5. Нажмите **Apply**. Дождитесь сборки (первый раз ~2–4 минуты).

Переменные окружения проставляются автоматически:
`DATABASE_URL`, `JWT_SECRET` (генерируется), `NODE_ENV=production`,
`COOKIE_SECURE=true`, `COOKIE_SAMESITE=none`,
`FRONTEND_URL=https://avestogroup2007.github.io`.

После деплоя бэкенд будет доступен по адресу вида
**`https://avesto-crm-backend.onrender.com`**, проверка:
`https://avesto-crm-backend.onrender.com/api/health` → `{ "ok": true }`.

### Демо-пользователи (по желанию)

Чтобы завести демо-учётки для входа, в панели Render:
**avesto-crm-backend → Shell** и выполнить:

```bash
npm run seed
```

(Логины `director / finance / manager / …`, пароль `changeme123` — сменить позже.)

### iiko — обязательные переменные

Ключи iiko живут **только** в переменных окружения Render, не в git:
**avesto-crm-backend → Environment → Add Environment Variable**

Отчётный сервер iikoServer (продажи, себестоимость, кадры, явки, кассовые
смены, закупки) — без этих трёх разделы отвечают «интеграция не настроена»:

- `IIKO_SERVER_URL` — адрес **без** `/resto/api`, со схемой: `https://ваш-хост.iiko.it`
- `IIKO_SERVER_LOGIN` — логин пользователя iikoOffice с правом на внешний API
- `IIKO_SERVER_PASSWORD` — его пароль (SHA1 считает сам сервис)

Ночной прогрев кэша отчётов (без него первый пользователь утром ждёт ~17 с):

- `IIKO_WARM_SECRET` — любая длинная случайная строка

iiko Лояльность (iikoCloud, нужен только для CVM) — опционально:

- `IIKO_LOYALTY_API_LOGIN`, `IIKO_LOYALTY_ORG_ID`

### Что сделать на сервере ПОСЛЕ первого деплоя

Код сам по себе всё не включит — четыре шага руками, иначе разделы будут
пустыми, хотя ошибок не покажут:

1. **Привязать филиалы к подразделениям iiko.** Админ-панель → «Филиалы и
   бюджеты» → у каждого филиала поле «iiko». Имена пишутся **дословно**, с
   префиксом и пробелом: `AC Микрорайон`, `AC Узбекистанский`, `AC Аэропорт`,
   `AS Наврузий цех`, `AC Наврузий Магазин`, `ICG Кейтеринг`. Точный список
   отдаёт `/resto/api/corporation/departments`. Любое расхождение — и фильтр
   по филиалу молча возвращает пустоту, а «все филиалы» работают.

2. **Синхронизировать кадры.** Админ-панель → «Сотрудники» →
   «Синхронизировать в систему». Подтягивает сотрудников, должности и
   подразделения. Роли ставятся только при создании учётки: уже заведённым
   сотрудникам роль назначается вручную в той же вкладке.

3. **Загрузить закупки.** «Закупки и склад» → «Синхронизировать из iiko» за
   нужный период. До этого все счётчики раздела — нули: он читает свою таблицу
   `ProcurementEntry`, а не iiko напрямую.

4. **Включить модули** (чек-листы, CVM) — это делает владелец системы в Back
   Office. Без включения вкладки «Рабочие зоны» и «Чек-листы» не видны.

### Прогрев кэша по расписанию

Render → New → Cron Job, раз в сутки ночью:

```
curl -X POST -H "X-Cron-Secret: <значение IIKO_WARM_SECRET>" \
  https://avesto-crm-backend.onrender.com/api/iiko-cron/warm
```

Греет пресеты интерфейса (сегодня, вчера, недели, месяцы) по сети и по каждому
филиалу. Отчёты за закрытые периоды в кэше не протухают и повторно из iiko не
тянутся.

### Важно про бесплатный тариф Render

- Веб-сервис на free засыпает после ~15 минут простоя; первый запрос после сна
  «будит» его ~30–50 секунд (для теста нормально).
- Бесплатный PostgreSQL на Render ограничен по сроку — для постоянной работы
  позже переключимся на платный план или другую базу (Neon/Supabase).
